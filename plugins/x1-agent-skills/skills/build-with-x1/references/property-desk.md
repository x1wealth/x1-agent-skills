# Property desk

Answer which parties are named for a particular property, what role each source gives them, and what the person can check next. Use their property identifiers and preferred visual style.

## Use it

“Using these records, tell me which party each document names for this property. Put its role, source and date beside the answer. I just want the answer here.”

An evidence table may be the complete result. A deed's dated grantee, an invoice's customer and a draft's proposed recipient are different roles. Match the property itself, not only a party's name. Present legal title needs evidence that establishes it; a historical deed alone isn't a current-title check.

## Make it mine

“Make an editable property desk right here. I'd like a little neighborhood with selectable houses and the source details one click away. Keep the evidence when we change the design.”

Use authorized supplied records immediately in an established private destination. Qualify artifact-side access separately from chat tools. Chat-mediated refresh can read again and update the view. If only a snapshot is available, describe it in the handoff; the design doesn't need a standing warning banner.

## Extend my project

“Add this view to my existing project. Keep my stack and property identifiers. Separate presentation from the source-reading adapter so I can change the design.”

An illustrative local interface is `loadRows(): Promise<PartyRow[]>`. It belongs to the project, not X1's tool schema. Define fields from the question and returned evidence; use the actual mounted connection to implement reads. Don't invent an endpoint or put access tokens in browser code.

Check the same property's historical deed and unsigned transfer, a different property's document, a rental invoice and an absent source date. Preserve the source's date label: document, signing and recording dates aren't interchangeable. A visual edit must retain the source and role, and a refresh mustn't silently write to the household record.
